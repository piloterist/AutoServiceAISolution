# Контекст проекта для Claude Code — распознавание номеров и контроль занятости боксов СТО

Дата актуализации: 2026-11-03. Язык общения и документации: русский.

## 1. Цель и бизнес-сценарий

Разработать прототип системы видеоконтроля ремонтных боксов автосервиса, которая автоматически определяет **факт въезда автомобиля в конкретный бокс, его государственный регистрационный номер и время въезда**, а затем **факт выезда и время выезда**. События в перспективе интегрируются с системой планирования загрузки боксов и заказ-нарядами (ЗН).

Начальная площадка — **один автосервис, 5 отдельных боксов**, один автомобиль в каждом. Потенциальное расширение в пределах той же площадки — **до 10 камер**, включая новые цеха. В будущем возможно обнаружение/подсчёт людей и, отдельно при наличии законных оснований и требований к приватности, идентификация конкретных людей. **Расширение на другие автосервисы не планируется**.

Бизнес-логика: после уверенного въезда в бокс фиксировать событие, найти/сопоставить существующий ЗН по номеру и начать интервал занятости бокса в планировщике; при подтверждённом выезде завершить интервал. **Не закрывать автоматически финансовый/учётный ЗН по одному событию выезда:** возможны тест-драйв, временный выезд, возвращение, смена бокса. Один ЗН может иметь несколько интервалов занятости.

## 2. Физическая среда и принципиальные ограничения

- В каждый бокс автомобиль **въезжает передом, выезжает задним ходом через те же ворота**.
- Ворота **без автоматики**, сигналов управления воротами нет.
- Камера может располагаться на противоположной от ворот стене; расстояние до въезжающего автомобиля меняется ориентировочно **от 8 м до 3 м**. Свет в боксе в целом хороший и постоянный; скорость движения низкая.
- Автомобиль поднимают на подъёмнике, он может частично или полностью **исчезнуть из поля зрения камеры, не выезжая из бокса**. Следовательно, **исчезновение автомобиля/номера из кадра НЕ является доказательством выезда**.
- Определять направление и факт пересечения **виртуальной контрольной линии/зоны у ворот**, если геометрия кадра позволяет. Важно проверять, видны ли сами ворота/контрольная зона при установке камеры на дальней стене.
- Выезд может фиксироваться по трекингу уже известного автомобиля без повторного OCR заднего номера, если направление и пересечение линии подтверждены. Нельзя завершать сессию только по потере трека.
- Дедупликация повторных срабатываний, временная задержка/гистерезис при неоднозначном движении, ручная коррекция, фото- и событийный журнал обязательны для пригодного MVP. Значение задержки (например, 15–30 с) — **гипотеза для тестирования**, не жёсткое требование.
- Если одной камеры недостаточно для достоверного определения пересечения ворот, в будущем рассмотреть дополнительный датчик на воротах (например, пару направленных фотоэлектрических датчиков), но **в прототипе датчики не покупать**.

## 3. Фактически приобретённая камера — НЕ Wi-Fi

**TP-Link VIGI C440, БЕЗ суффикса W, объектив 4 мм согласно выбранному/заказанному варианту — точную фокусную длину проверить в интерфейсе/по шильдику.** Важно не путать с VIGI C440-W, которая обсуждалась до покупки. **У фактической камеры Wi-Fi нет.**

Фактически выполнено:
- Камера подключена к электропитанию и **Ethernet-кабелем к роутеру**.
- Windows-компьютер подключён к Wi-Fi того же роутера.
- IP компьютера по Wi-Fi: **192.168.31.122/24**, шлюз **192.168.31.1**.
- IP камеры: **192.168.31.209**; в интерфейсе роутера устройство отображается как **IPC**; MAC **9C:2A:F4:DA:22:EA**.
- `ping 192.168.31.209`: 4/4 ответов, 0% потерь, средняя задержка около 5 мс.
- `Test-NetConnection` с Windows:
  - TCP 80: `False` (HTTP недоступен).
  - TCP 443: `True` (HTTPS доступен).
  - TCP 554: `True` (порт RTSP открыт).
- **https://192.168.31.209** успешно открыт, пользователь **вошёл под admin** и видит **живое изображение** на странице TP-Link VIGI (разделы Preview / Information / Settings). На скриншоте виден поток с камеры и экранная дата/время.
- **RTSP-видеопоток в VLC, FFmpeg или OpenCV ещё НЕ проверен**. Открытый TCP 554 доказывает доступность порта, но не успешную авторизацию и получение кадров.
- Пароль администратора НЕ передавался и не должен попадать в чат, git, логи или код.

**Примечание:** в более раннем обсуждении была физически доступная **HiWatch IPC-B040(B), 2.8 мм**. Для текущего прототипа используется именно **купленная TP-Link VIGI C440 (без W)**; HiWatch не подменять и не считать подключённой.

## 4. Компьютер и размещение

Для **прототипа** используется уже имеющийся Windows-компьютер (VS Code + Claude Code), поэтому **не нужно покупать сервер, NVR, GPU или вторую камеру**. При необходимости использовать Python и FFmpeg, виртуальное окружение, OpenCV.

**Продакшен**: один постоянно работающий локальный вычислительный узел на площадке (предпочтительно проводной Ethernet к роутеру) обрабатывает камеры и отправляет **события и снимки** в облако по исходящему HTTPS. Отдельного постоянно работающего ПК сейчас нет. Альтернатива с непрерывным облачным видеопотоком обсуждалась, но не выбрана как базовая из-за сетевой сложности и затрат.

Для 5–10 камер обсуждался готовый расширяемый системный блок, ориентир: Intel Core i5-14400 со встроенной графикой/Quick Sync, 32 ГБ RAM, NVMe SSD 1 ТБ, свободный PCIe x16, качественный БП с запасом для будущей NVIDIA GPU, Ubuntu Linux. Это **предварительная рекомендация, не купленная конфигурация и не измеренное требование**. GPU с 12–16 ГБ VRAM может потребоваться для более сложной аналитики людей, но **сейчас не нужен по умолчанию**. Окончательные ресурсы определить по профилированию прототипа.

## 5. Облачная система и интеграция

У пользователя уже есть отдельная система аналитики/планирования автосервиса: **FastAPI + PostgreSQL + Next.js**, развёртывание через Docker в **Timeweb Cloud App Platform**. Существующая система получает данные из 1С Альфа-Авто. Нельзя предполагать, что код, API, модели БД и схема аутентификации доступны в текущем репозитории Claude Code: сначала изучить workspace и спросить, где находится проект, если интеграция требуется.

Предлагаемый поток данных:

`VIGI C440 (LAN / RTSP) -> Windows Python worker (прототип) -> локальные события/SQLite/фото -> [позже] HTTPS API FastAPI на Timeweb -> PostgreSQL -> Next.js планировщик`.

В будущем локальный worker должен уметь повторять отправку при потере интернета, обеспечивать идемпотентность событий, не терять события при перезапуске, хранить технический журнал и минимально необходимые снимки. Не выставлять RTSP или админ-панель камеры в публичный интернет. Секреты только в `.env`/защищённых настройках, `.env` в `.gitignore`.

## 6. Предлагаемая модель событий и состояний

Состояния для каждого бокса (предварительная схема): `EMPTY`, `ENTERING`, `OCCUPIED`, `EXIT_CANDIDATE`, `UNKNOWN/REVIEW`.

События: `plate_observed`, `entry_candidate`, `entry_confirmed`, `exit_candidate`, `exit_confirmed`, `manual_correction`. Полезные поля: `event_id`, `camera_id`, `bay_id`, `timestamp` с часовым поясом, `event_type`, `plate_raw`, `plate_normalized`, `ocr_confidence`, `track_id`, `direction`, `snapshot_path`, `work_order_id` (nullable), `review_status`.

Это **предлагаемый контракт**, а не существующая БД. Начинать с простого локального JSONL/SQLite; согласовать схему API и существующие сущности до интеграции. Если номер прочитан неуверенно, не назначать ЗН автоматически; отправлять на ручную проверку.

## 7. Поэтапная разработка — выполнять инкрементально

### Этап 0 — инвентаризация среды
- Посмотреть текущую папку VS Code и существующие файлы; не перезаписывать пользовательский проект.
- Уточнить ОС, Python, FFmpeg/VLC, доступные ресурсы CPU/GPU; проверить установленное ПО.
- Проверить параметры камеры в веб-интерфейсе: **точный вариант C440, объектив, main/substream, кодек H.264/H.265, разрешение, FPS, дата/часовой пояс, параметры RTSP**.

### Этап 1 — получить поток и сохранить доказательства работоспособности
- Подключиться к RTSP локально, не раскрывая пароль в терминальной истории, логах и git.
- Проверить официальный синтаксис RTSP для **VIGI C440 без W** по документации TP-Link. Не считать путь RTSP проверенным, пока не получены кадры.
- Получить и показать кадр, затем записать короткий тестовый ролик; сохранить метаданные потока (разрешение, FPS, кодек, задержка, пропуски кадров).
- Проверить восстановление подключения после кратковременного разрыва сети.

### Этап 2 — номерные знаки
- Использовать реальные кадры с автомобилем на 3, 5 и 8 м; по возможности в дневном/вечернем освещении и с бликами фар.
- Протестировать локальный детектор автомобиля/номерной пластины и OCR **российских регистрационных знаков**; нормализация кириллических/латинских похожих символов и форматов РФ.
- Собирать метрики: доля правильных распознаваний, ошибки символов, latency, CPU/RAM, FPS.
- Не утверждать, что камера имеет аппаратное ANPR: распознавание выполняет собственное ПО.

### Этап 3 — въезд, выезд и подъёмник
- Определить ROI/виртуальную линию ворот на реальном изображении. Если линия не видна, не симулировать успешное обнаружение выхода.
- Отслеживать движение и направление, подтверждать пересечение контрольной зоны, связывать OCR с треком и состоянием бокса.
- Тестовые сценарии: въезд, остановка, перемещение внутри бокса, подъём на подъёмнике/исчезновение из кадра, опускание, выезд задним ходом, остановка возле ворот, частичный выезд и возвращение, повторный въезд, смена бокса, два разных автомобиля последовательно, потеря сети/кадров.
- Никакого завершения интервала только по исчезновению объекта.

### Этап 4 — журнал и UI
- Локальный журнал событий с кадром, номером, временем, боксом, уверенностью, статусом подтверждения и ручной коррекцией.
- Минимальный экран состояния бокса (свободен/занят/нужна проверка).

### Этап 5 — интеграция и масштабирование
- После согласования API отправлять события в FastAPI на Timeweb, связывать с ЗН, обновлять интервалы планировщика.
- Масштабировать на 5 камер, затем оценивать до 10; профилировать нагрузку, по необходимости использовать аппаратное декодирование, обработку уменьшенных кадров и запуск OCR по событию.
- Распознавание/идентификация людей — **отдельная будущая фаза**, не смешивать с MVP и отдельно проработать законность, доступы и сроки хранения данных.

## 8. Важные инженерные решения и ограничения

1. **Сначала RTSP и реальный кадр**, потом модели компьютерного зрения. Не строить большой сервис до проверки базового видеопотока.
2. **Нельзя гарантировать точность OCR по паспортным мегапикселям.** Объектив 4 мм потенциально лучше для номера на расстоянии, чем широкоугольные 2.8–3.17 мм, но реальный результат зависит от света, выдержки, ракурса и компрессии.
3. **Встроенное пересечение линии в VIGI** (если есть в конкретной модели/прошивке) не равно доступному внешнему API и не равно надёжному обнаружению выезда. Для MVP можно реализовать свою аналитику.
4. Подключение камеры **проводное**, отсутствие Wi-Fi у купленной C440 — осознанное ограничение; компьютер может оставаться на Wi-Fi для тестов.
5. Не требовать немедленно купить GPU, NVR, дополнительную камеру или датчики.
6. Не считать открытый TCP 554 подтверждением RTSP-видео.
7. Не публиковать логины, пароли, кадры с людьми/номерами или IP облачных сервисов в публичный репозиторий.
8. Не закрывать бухгалтерский ЗН по одному выезду. Интервалы нахождения в боксе — отдельная сущность.

## 9. Первое задание Claude Code

**Сделай минимальный воспроизводимый прототип подключения к уже работающей TP-Link VIGI C440 (без W) на `192.168.31.209` из Windows.**

1. Изучи текущий workspace и существующий код; не ломай его.
2. Проверь доступные зависимости и предложи минимальный стек (Python, FFmpeg/OpenCV).
3. Сверь официальный RTSP URL для этой модели; при необходимости попроси пользователя посмотреть настройки камеры. Не проси передать пароль в чат.
4. Реализуй конфигурацию через переменные окружения, безопасный ввод секрета, проверку подключения, сохранение одного кадра и короткого ролика.
5. Покажи точные команды запуска, ошибки с понятной диагностикой и фактический результат.
6. После подтверждения кадров предложи следующий небольшой шаг: сбор тестового набора для распознавания российских номеров.

**Работай итеративно: сначала успешный RTSP и кадр; без преждевременной реализации полного backend, UI и нейросетевого пайплайна.**
